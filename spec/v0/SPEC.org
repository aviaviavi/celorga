#+title: Org2 Specification v0 (Draft)

This is the initial, intentionally-scoped Org2 specification.

The primary goal of v0 is to define a *lossless, round-trippable parse* of Org-like documents into a *canonical AST*.

* v0 at a glance

This document is intended to be a compact, self-contained overview of what Org2 v0 standardizes.

- Primary contract: parse text into a canonical AST with lossless round-trip guarantees.
- Primary syntax families in v0: headlines, drawers/properties, directives/comments, source/common/special/dynamic blocks, lists, tables, timestamps, links, emphasis, scholarly inline objects, keyword lines, and planning lines.
- Compatibility posture: standard Org forms remain canonical; selected Org2 syntax sugar/aliases are additive.
- Semantic posture: parsing is normative in v0; most higher-level behavior modules (agenda/workflow/export semantics) are intentionally deferred.

Related docs:
- Normative surface grammar: [[file:GRAMMAR.ebnf][GRAMMAR.ebnf]]
- Deterministic precedence and AST-construction rules: [[file:PARSING.org][PARSING.org]]
- Conformance rules and invariants: [[file:CONFORMANCE.org][CONFORMANCE.org]]
- Native org-roam-style module draft (v0 scope proposal): [[file:ROAM.org][ROAM.org]]

* Scope

** In scope (normative)
- Input text → canonical AST
- Surface grammar, contextual precedence, and AST-construction algorithms
- Canonical AST schema and invariants
- Normative fixtures: =.org= input → =.json= AST output

** Out of scope (explicit, non-normative for v0)
- Emacs-specific TODO hooks and interactive state-change logging prompts
- Agenda behavior
- Clocking
- Property inheritance
- Export rules
- Editor behavior / UI

* Specification Model

Org2 is specified in layers:

** Layer 1: Syntax → Canonical AST (normative)

A compliant implementation MUST:
- Parse a document into the *canonical AST* described by [[file:canonical-ast.schema.json][canonical-ast.schema.json]].
- Preserve enough information to *round-trip* to the original bytes (modulo a future, explicitly-defined normalization layer).

The language contract is jointly defined by:
- Surface candidates: [[file:GRAMMAR.ebnf][GRAMMAR.ebnf]]
- Contextual precedence, grouping, and AST construction: [[file:PARSING.org][PARSING.org]]
- Per-construct requirements in this document
- The *canonical AST schema*: [[file:canonical-ast.schema.json][canonical-ast.schema.json]]
- Ambiguity examples: [[file:parsing-cases.json][parsing-cases.json]]
- The *normative fixtures* in =tests/=

These artifacts are jointly normative and MUST NOT intentionally conflict. A
contradiction among them is a specification defect to be resolved explicitly,
not permission for an implementation to select whichever artifact it prefers.

An optimized hand-written parser, generated parser, Tree-sitter grammar, or
other implementation strategy is conforming when its observable AST,
diagnostics, and round-trip output satisfy this contract. No production parser
implementation is itself the language definition.

** Layer 2: Semantic modules (future, normative, scoped)

Semantics are defined as independent modules that operate on the canonical AST.

Examples (not yet specified):
- =org2-sem-todo=
- =org2-sem-time=
- =org2-sem-properties=
- =org2-sem-links=

An implementation may support any subset of modules, but MUST be explicit about which modules (and which versions) it supports.

* Additive syntax sugar and aliases (v0)

Org2 v0 keeps Org begin/end and inline forms as canonical, while allowing a small set of additive shorthand forms:

- Fenced source blocks: =```lang= ... =```=
  - Parsed as =SrcBlock=.
  - Additive sugar only; parsers MUST remain compatible with =#+begin_src= / =#+end_src=.
  - The fence marker is exactly three backticks; four-or-more backticks are ordinary text in v0.
- Org2 source alias: =#+begin_org2= ... =#+end_org2=
  - Parsed equivalently to =#+begin_src org2= ... =#+end_src= in v0.
- Backtick inline code: =`...`=
  - Parsed as inline code emphasis (same =kind: "code"= target as ~=...=~).

These sugar forms are conveniences, not a replacement for standard Org forms.
The lossless parser and default printer preserve whichever spelling was read.
Org2-controlled writers that persist edited ordinary =.org= documents MUST
select the *canonical Org serialization profile*, which rewrites fenced source blocks
to =#+begin_src= / =#+end_src=, =#+begin_org2= aliases to
=#+begin_src org2= / =#+end_src=, and representable backtick inline code to
ordinary Org inline-code markup, preferring tilde delimiters and using equals
delimiters when the content itself contains a tilde. Sugar is preserved when
rewriting would make a literal =#+end_src= body line or inline delimiter
ambiguous.
File-based formatting MUST infer this profile for =.org= targets. Buffer and
stdin writers without a filename MUST select it explicitly when the intended
target is =.org=. Existing =.org2= documents retain the default lossless
round-trip behavior unless a caller explicitly requests canonical Org output.

* Native org-roam support (v0 status)

Org2 v0 includes parser-level primitives needed for org-roam-style workflows (notably IDs, ID links, file/headline structure, and lossless links), and tracks a native roam module as a first-class direction.

Current status:
- Parser support is normative in this spec.
- Roam behavior module details (indexing/backlinks/dailies/database conventions) are documented in [[file:ROAM.org][ROAM.org]] as a v0 draft.
- Source of truth remains plain files; any roam database is a derived cache.

Practical implication: a reader can treat roam as a native Org2 capability direction, with the parser contract stable here and operational semantics evolving in the companion roam document.

* Versioning

- This directory is =spec/v0/=.
- Additive, backwards-compatible changes MAY be made within v0 as patch revisions.
- Breaking changes MUST be done in a new spec version directory (e.g. =spec/v1/=).

* Normative fixtures

Fixtures live in =tests/=:
- =NNNN-*.org= is the input
- =NNNN-*.json= is the canonical AST output

Implementations SHOULD run these fixtures as golden tests.

Small inputs whose purpose is to settle overlapping interpretations live in
=parsing-cases.json=. Implementations SHOULD run those cases in addition to the
larger golden fixtures.

* Headlines (subheadings)

** Headline syntax

A *headline line* is a line that matches:

- One or more =*= characters at the start of the line.
- Exactly one space after the =*= run.
- A non-empty title string after that space.

A headline line produces a =Headline= node with:

- =level=: the number of =*= characters.
- =title=: an array of inline nodes, parsed using the same inline rules as paragraphs (timestamps, links, emphasis, etc.).

** TODO keywords and terminal states

A headline title MAY begin with a TODO keyword.

The built-in TODO keywords are:

- =TODO=
- =IN_PROGRESS=
- =DONE=
- =CANCELED=
- =CANCELLED=

Example:
- =* TODO Fix bug= produces a =Headline= with =todo: "TODO"= and =title: "Fix bug"=.
- =* DONE Ship docs= produces a =Headline= with =todo: "DONE"= and =title: "Ship docs"=.

State transitions preserve the declared keyword. Terminal states represent tasks that require no further action.

A document MAY extend the parsed vocabulary with =#+TODO:=, =#+SEQ_TODO:=, or =#+TYP_TODO:=. The parser MUST strip fast-selection/logging suffixes in parentheses from keyword names. Keywords before =|= are active; keywords after it are terminal. If =|= is absent, only the final keyword is terminal. Multiple declarations define separate sequences. The exact declared keyword is stored in =todo=. Declarations inside blocks or drawers MUST NOT configure the document. Built-in keywords remain available; a declaration overrides their active/terminal classification.

Corpus configuration MAY provide =todo.sequences=, an array of Org-style sequence strings in =org2.json=. Each configured sequence MUST contain at least one active and one terminal keyword, with no duplicate state names across sequences. File-local declarations take precedence over corpus defaults. An empty array restores the built-in vocabulary. File-aware clients MUST resolve defaults from the nearest corpus configuration and MUST invalidate derived TODO metadata when that configuration changes. Parsing without file context uses only the supplied document declarations and built-in vocabulary.

Documents with declarations or configured defaults expose =todoSequences= (arrays of =keywords= and =terminal= strings); their task headings expose the resolved boolean =todoTerminal=. Documents without declarations or configured defaults omit these fields for compatibility. Cycling follows the owning sequence and wraps to its first keyword. Entering a terminal keyword writes =CLOSED= metadata; returning to an active keyword removes it. Optional transition logbooks record exact old and new keywords, including changes between two terminal states. Fast-selection keys and Emacs logging prompt annotations are accepted syntax, not interactive UI bindings.

** Priority and COMMENT metadata

An optional =[#A]= through =[#Z]= or =[#0]= through =[#9]= cookie following the TODO keyword MUST be stored in the dedicated =priority= field without remaining in =title=. An Org =COMMENT= marker in headline metadata MUST set =commented: true=.

** Tags (syntax only)

A headline title MAY end with a tag group:
- tag group syntax is =:tag1:tag2:=
- it MUST appear at the end of the headline
- tags MUST NOT contain whitespace

Example:
- =* Plan release :ops:launch:= produces =tags: ["ops", "launch"]= and =title: "Plan release"=.

** Headline nesting

Headlines form a tree via their =children= arrays.

When a headline of level =L= is parsed:

- It becomes a child of the nearest preceding headline whose level is *strictly less than* =L=.
- If there is no preceding headline with level =< L=, the headline becomes a direct child of the =Document=.
- All subsequent non-headline nodes (e.g. paragraphs) attach to the most recent headline (at any level) until a new headline changes the current container.

** Level skips

Level skips are allowed and deterministic.

For example, a level-3 headline (=***=) immediately after a level-1 headline (=*=) becomes a child of that level-1 headline; no implicit level-2 headline nodes are created.

* Property drawers (syntax only)

Property drawers are supported as a structural syntax element.

Property inheritance and other property semantics are out of scope for v0.

* Generic drawers

Generic drawers are supported as a structural syntax element.

A *drawer* begins with a line of the form =:NAME:= (where =NAME= contains no whitespace or =:=) and ends with a line exactly equal to =:END:=.

Generic drawers MUST be represented as =Drawer= nodes and preserved losslessly.

** Property drawer syntax

A property drawer is a block consisting of:

- A start line exactly equal to =:PROPERTIES:=
- Zero or more property lines
- An end line exactly equal to =:END:=

Property drawers produce a =PropertyDrawer= node.

** Property line syntax

A property line MUST match:

- A leading =:=
- A non-empty key (no whitespace, no =:=)
- A =:=
- Optionally a single space
- The value (possibly empty)

Example:

- =:ID: abc123= produces ={ key: "ID", value: "abc123" }=

Property drawers may appear as children of =Headline= nodes (and implementations MAY also support them at document level).

* Directives (unknown #+... lines)

Org2 v0 supports preserving directive lines that begin with =#+= but are not otherwise recognized as:
- keyword lines (=#+KEY: VALUE=), or
- structural blocks (e.g. =#+begin_src= ... =#+end_src=, =#+begin_org2= ... =#+end_org2=, or fenced =```= source blocks)

Such lines MUST be represented as =DirectiveLine= nodes and preserved losslessly.

* Comment lines

A *comment line* is any line that begins with =#= but does not begin with =#+=.

Comment lines MUST be represented as =CommentLine= nodes and preserved losslessly.

* Comment blocks

Comment blocks are supported as a block syntax element.

A *comment block* begins with =#+begin_comment= and ends with =#+end_comment=.

Comment blocks MUST be represented as =Block= nodes with =kind: "comment"= and preserved losslessly.

* SOURCE blocks (#+begin_src / #+end_src)

Source blocks are supported as a structural syntax element.

Canonical begin/end form remains =#+begin_src= / =#+end_src=.

=#+begin_org2= / =#+end_org2= are supported as a *shorthand alias* for an Org2 source block (equivalent to =#+begin_src org2= / =#+end_src= for the purposes of parsing in v0).

Fenced triple-backtick blocks (=``` ... ```=) are also supported as *additive syntax sugar* only. They are not a replacement for Org begin/end source blocks, and parsers MUST remain backwards compatible with =#+begin_src= / =#+end_src= forms.

Executing source blocks and interpreting header args (babel semantics) are out of scope for v0.

* Other block and element syntax

- Any =#+begin_NAME= / =#+end_NAME= pair not reserved for a source alias MUST produce a =Block= whose =kind= is =NAME= in lowercase. Its body remains lossless raw text.
- =#+begin: NAME PARAMS= / =#+end:= MUST produce a =DynamicBlock=. Dynamic-block writer execution is out of scope.
- Consecutive lines beginning with =: = MUST produce a =FixedWidth= node.
- A line containing five or more hyphens (and optional surrounding whitespace) MUST produce a =HorizontalRule=.
- =\begin{NAME}= / =\end{NAME}= pairs MUST produce a =LatexEnvironment= with raw body text.
- A line beginning with =%%(= MUST produce a =DiarySexp=.

* Tables (pipe tables)

Org2 v0 supports Org-mode style *pipe tables*.

** Table row syntax

A *table row line* is a line that:

- Begins with =|= (optionally after indentation spaces), and
- Ends with =|= (ignoring trailing whitespace).

The bytes between pipes are trimmed into compatible cell strings and also parsed into inline objects.

A table row line produces a =TableRow= node with:

- =cells=: the existing array of trimmed strings, retained for compatibility and deterministic table formatting.
- =contents=: a parallel array whose entries contain canonical inline nodes for each cell.

Examples:

- =|a|b|= → =cells: ["a", "b"]=
- =| a | b |= → =cells: ["a", "b"]=
- =||= → =cells: [""]=
- =|a||b|= → =cells: ["a", "", "b"]=

** Table formulas

One or more =#+TBLFM:= lines immediately following a pipe table MUST be attached to that =Table= as ordered =TableFormulaLine= nodes. Each line retains its complete raw source and exposes =::=-separated assignments with =targetRaw=, =expressionRaw=, and optional =modeRaw=. Printers MUST preserve formula lines even when an expression is not executable by Org2.

The shared evaluator supports safe deterministic spreadsheet expressions: field, row, column, and rectangular-range targets; absolute, relative, and A1 references; arithmetic, comparisons, boolean operators, vector aggregates, common numeric functions, numeric formats, and duration modes. Column assignments begin after the first hline. Later assignments replace earlier assignments for the same cell.

Recalculation MUST be atomic: if any selected assignment is invalid, refers outside the table, or requests an unsupported execution mechanism, no cell may be changed. Emacs Lisp forms, remote-table execution, and arbitrary Calc extensions are outside the v0 execution boundary and MUST remain losslessly preserved.

** Hline row syntax

A *table hline row line* is a table row line where, after trimming leading/trailing whitespace, the line matches:

- =|= followed by one or more =-= or =+= characters, followed by =|=

Example:
- =|---+---|= produces a =TableHline= node.

** Table grouping and termination

A =Table= node spans one or more consecutive table row lines and/or hline row lines.

The parser MUST terminate a =Table= at the first subsequent line that is not a table row line.

** SOURCE block syntax

A source block is a block consisting of:

- A begin line matching one of:
  - =#+begin_src= or =#+begin_org2= (case-insensitive), with optional indentation, or
  - a fenced code opener line starting with exactly three backticks (=```=) and optional trailing language token bytes. A line starting with four-or-more backticks is not a fenced opener in v0.
- Zero or more body lines (treated as raw text).
- A matching end line:
  - =#+end_src= or =#+end_org2= for begin/end style blocks, or
  - a fenced closer line of exactly three backticks (=```=) for fenced blocks.

The parser MUST treat the body as raw text until it encounters the matching end marker line.

** Lossless capture

A =SrcBlock= node MUST capture enough information to reproduce the exact original bytes of:

- The begin marker line (indentation, keyword spelling, and all bytes after the keyword).
- The block body (all bytes between the end of the begin marker line and the start of the end marker line).
- The end marker line (indentation, keyword spelling, and all bytes after the keyword).

In v0, the canonical AST captures begin/end marker lines as:

- =begin.indent=, =begin.keywordRaw=, =begin.afterKeywordRaw=
- =end.indent=, =end.keywordRaw=, =end.afterKeywordRaw=

For fenced blocks, =keywordRaw= is =```= and =afterKeywordRaw= captures any trailing language token bytes on the opener line.

** Unterminated blocks

If a begin marker is not terminated by a matching end marker before end-of-file, the parser MUST emit a =SrcBlock= node with:

- =terminated: false=
- =end= omitted
- =bodyRaw= containing all remaining bytes until end-of-file

* Lists

Org2 v0 supports both *bullet lists* and *ordered lists* with full nesting support and optional checkbox markers.

** List syntax

A *list item line* matches one of:

- =- = followed by optional checkbox and content (bullet list)
- =+ = followed by optional checkbox and content (bullet list, alternative marker)
- An indented =* = followed by optional checkbox and content (at column zero, =* = remains a headline)
- =<digits>.= or =<digits>)= followed by space, optional checkbox, and content (ordered list)

Examples:
- =- apples= → unordered list item with content "apples"
- =- [ ] unchecked task= → unordered list item with unchecked checkbox
- =- [X] completed task= → unordered list item with checked checkbox (both =[X]= and =[x]= are recognized)
- =1. first= → ordered list item with content "first"
- =1) [x] done= → ordered list item with checked checkbox

The canonical AST records =ordinal= on a =ListItem= when the written number
differs from its implicit one-based position in that =List=. This preserves
explicit starting numbers and discontinuous numbering when blank lines or rich
child blocks split an ordered list into multiple AST fragments.

** Checkbox syntax

A *checkbox* is an optional marker that appears at the start of list item content:

- =[ ]= → unchecked, creates =checkbox: "unchecked"= on the =ListItem=
- =[X]= or =[x]= → checked, creates =checkbox: "checked"= on the =ListItem=
- =[-]= → partial/indeterminate, creates =checkbox: "indeterminate"= on the =ListItem=

The checkbox MUST be followed by a space and then the item content.

Progress cookies are recognized as structured inline state:

- =[n/m]= → fraction progress cookie; =[/]= is an empty refreshable placeholder
- =[p%]= → percentage progress cookie; =[%]= is an empty refreshable placeholder

Org2 compile outputs also compute checkbox rollups over file/headline ranges and lint stale progress cookies whose displayed value no longer matches the checked checkbox count. Checked items count toward both the total and completed count; unchecked and indeterminate items count only toward the total. The expected percent value is =floor(100 × completed / total)=, except that it MUST be 1 when at least one item is completed and the rounded-down value is 0; it is 0 when there are no items. A fraction cookie's =percent= field in the canonical AST uses the same rule. Empty progress placeholders are stale whenever their owner can be evaluated and are refreshed to the corresponding numeric form. A top-level stale-cookie issue MUST use the narrowest heading range containing that cookie's line, or the file preamble before the first heading. A wider ancestor's recursive rollup MUST NOT override the cookie owner's evaluation.

An optional =[@N]= counter cookie before the checkbox MUST be stored as =counter: N=. A =term :: definition= item MUST store the parsed term in =descriptionTag= and the definition as its ordinary children.

** Nested lists

A list item whose indentation is greater than the previous item becomes a child of that item. The parser creates a nested =List= node within the parent =ListItem='s =children= array.

Nested lists MAY have a different =ordered= value than their parent (e.g., an ordered list containing bullet list items, or vice versa).

Example:

#+begin_src org
- [ ] Parent task
  - [X] Completed subtask
  - [ ] Incomplete subtask
- Another parent
  1. Nested ordered
  2. More nested
#+end_src

Produces nested =List= nodes where the subtasks are items of a nested unordered list under the first parent, and the nested ordered items are under the second parent.

** Nesting rules

- A line with greater indentation than the previous list item becomes a child list item.
- A blank line terminates the current list (and all nested lists).
- A line that is not indented at least to the list marker column ends the list.
- Paragraph continuation lines within a list item MUST be indented to at least the marker column.

* Timestamps (dates)

Org2 v0 supports capturing Org-mode timestamp/date syntax in a *lossless* form.

Timestamp semantics (agenda scheduling, recurrence evaluation, and normalizing day-of-week strings) are out of scope for v0.

** Timestamp syntax

A *timestamp* is an inline construct with one of two delimiters:

- *Active*: =<...>=
- *Inactive*: =[...]=

A timestamp MUST begin (inside the delimiters) with a date prefix:

- =YYYY-MM-DD= (exactly 4 digits, =-=, 2 digits, =-=, 2 digits)

All bytes inside the delimiters after the date prefix are treated as raw content (may include day-of-week, time, repeaters, warnings, etc.).

Examples:

- =<2026-01-16 Fri>=
- =[2026-01-16 Fri]=
- =<2026-01-16 Fri 13:45>=
- =<2026-01-16 Fri 10:00-11:00>=
- =<2026-01-16 Fri +1w -2d>=

** Timestamp ranges

Org supports expressing ranges between two timestamps.

In v0, a *timestamp range* is captured as a single inline node containing:

- =start=: a =Timestamp=
- =separatorRaw=: the exact bytes between the end of the start timestamp and the beginning of the end timestamp
- =end=: a =Timestamp=

The reference parser recognizes ranges when two timestamps are separated by =--=, optionally with spaces.

Examples:

- =<2026-01-16 Fri>--<2026-01-18 Sun>=
- =<2026-01-16 Fri> -- <2026-01-18 Sun>=

* Inline emphasis (bold/italic/underline/strike/verbatim/code)

Org2 v0 supports a limited, “80% coverage” subset of Org inline emphasis.

** Markers

The following emphasis markers are recognized:

- ~*...*~ → =kind: "bold"=
- ~/.../~ → =kind: "italic"=
- ~_..._~ → =kind: "underline"=
- ~+...+~ → =kind: "strike"=
- ~=...=~ → =kind: "verbatim"=
- ~~...~~ → =kind: "code"=
- =`...`= → =kind: "code"= (Org2 additive syntax sugar)

Each emphasized span produces an =Emphasis= inline node:

- =type: "Emphasis"=
- =kind=: one of the above
- =marker=: the opening/closing marker character
- =content=: the raw inner bytes (v0: a string; no inline children)

** Boundary rules (v0)

Emphasis is only recognized when it is bounded such that it is unlikely to match “inside words”.

An emphasis span starting at byte index =i= with marker =M= is valid iff:

- Opening marker =M= is preceded by a boundary (start-of-string, whitespace, or non-word character).
- The byte after opening marker is not whitespace.
- A matching closing marker =M= exists later on the same line.
- The byte before the closing marker is not whitespace.
- The byte after the closing marker is a boundary (end-of-string, whitespace, or non-word character).

For v0, “word character” means ASCII =[A-Za-z0-9]=.

Backtick code spans (=`...`=) are additive syntax sugar and follow the same boundary rules as other inline emphasis markers in v0.

** Nesting

Nesting is not supported in v0. Any marker bytes inside =content= are treated as plain text.

* Rich inline objects

Org2 v0 emits dedicated inline nodes for the following non-executable Org objects:

- =FootnoteReference=: =[fn:LABEL]=, =[fn:LABEL:DEFINITION]=, or =[fn::DEFINITION]=. A line beginning with =[fn:LABEL]= produces a =FootnoteDefinition= element.
- =Citation=: =[cite:@KEY]=, optional style forms such as =[cite/t:@KEY]=, and semicolon-separated references with per-reference prefix/suffix text.
- =Target=: =<<TARGET>>= and radio =<<<TARGET>>>= forms.
- =Entity=: common Org entity names such as =\alpha=, =\copy=, and =\rarr=.
- =LatexFragment=: =$...$=, =$$...$$=, =\(...\)=, and =\[...\]=.
- =ExportSnippet=: =@@BACKEND:VALUE@@=.
- =Script=: braced or simple =_subscript= and =^superscript= suffixes.
- =LineBreak=: two backslashes at the end of a logical line.
- =Link= with =format: "angle"=: =<SCHEME:TARGET>=.

All of these nodes MUST retain =raw= bytes for deterministic printing. Rendering or resolving citations, bibliographies, entities, LaTeX, export backends, and radio links is a semantic module rather than a parser obligation.

Macro expansion, inline source blocks, inline Babel calls, and Babel execution are deliberately outside the v0 canonical AST. Their source bytes remain ordinary text or directives.

External plugins MUST NOT replace or mutate the v0 parser contract. A client
MAY interpret preserved source-block languages or other canonical nodes through
an additive, versioned extension API, but the underlying AST and deterministic
printer remain defined by this specification. Plugin manifests, locks, trust,
execution, and presentation sandboxing are runtime contracts rather than new
v0 syntax.

* Links (v0)

Org2 v0 supports a limited subset of Org links as inline nodes.

** Bracket links

A *bracket link* is an inline construct with the form:

- =[[TARGET]]=
- =[[TARGET][DESCRIPTION]]=

The canonical AST emits a =Link= inline node with:

- =format: "bracket"=
- =raw=: the exact matched bytes (including brackets)
- =targetRaw=: the raw target payload
- =descriptionRaw= (optional): the raw description payload

** Plain URLs

A *plain URL* is recognized when it begins with =http://= or =https://= and extends until the next whitespace.

To reduce accidental captures, the reference parser trims common trailing punctuation characters from the URL.

** Color bindings

Org2 reserves the custom bracket-link type =color:= for explicit, non-navigating color presentation. This is additive Org2 behavior over the ordinary =Link= node; the canonical AST and printer preserve the original bracket-link bytes.

Supported forms are:

- =[[color:VALUE][LABEL]]= for foreground shorthand
- =[[color:fg=VALUE][LABEL]]= or =[[color:foreground=VALUE][LABEL]]=
- =[[color:bg=VALUE][LABEL]]= or =[[color:background=VALUE][LABEL]]=
- =[[color:fg=VALUE;bg=VALUE][LABEL]]= for both

=text= is an alias for =fg=. Values are restricted to the portable Org2 named palette or =#RGB=/=#RRGGBB= literals. Empty labels, unknown keys, duplicate keys, unsupported values, and arbitrary CSS are not color bindings and retain ordinary link behavior.

Renderers apply a binding to its label wherever inline links are supported. When a binding is the sole content of a table cell, foreground and background apply to the whole cell. No meaning is inferred from table headers or unmarked color words.

** Parsing order (deterministic disambiguation)

When parsing inline content, the parser applies transformations in a deterministic order to avoid ambiguities:

1. Rich delimiter-led objects (targets, footnotes, citations, export snippets, LaTeX/entities, scripts, and hard line breaks)
2. Progress cookies and timestamps
3. Bracket, angle, and plain links
4. Emphasis markers, respecting boundary rules

This order ensures that:
- Links take precedence over emphasis (e.g., =[[url][*text*]]= parses as a link, not emphasis within a link)
- URLs are not split by emphasis markers
- Timestamps are not confused with emphasis markers
- Boundary rules are consistently applied

Within emphasis parsing, all marker types (=*=, =/=, =_=, =+=, ===, =~=) are processed with equal priority, processing left-to-right as they appear on the line.

* Keyword lines (#+KEY: VALUE)

Org2 v0 supports capturing file-level keyword/metadata lines as explicit nodes.

A *keyword line* matches:

- Optional indentation
- =#+=
- a key token (captured as =keyRaw=)
- =:=
- the remainder of the line (captured as =valueRaw=, including any leading space)

Keyword lines produce a =KeywordLine= node with a lossless =raw= field.

** Affiliated keywords

Some keyword lines are *affiliated metadata* when they appear immediately before a table, source block, or common block with no blank line or other element between them.

Recognized affiliated keys are matched case-insensitively:

- =NAME=
- =CAPTION=
- =HEADER= / =HEADERS=
- =RESULTS=
- =PLOT=
- =CHART=
- =DATASET=
- =VIEW=
- Any key beginning with =ATTR_=

When one or more affiliated keyword lines precede an eligible element, the parser MUST attach them to that element as =affiliatedKeywords= in source order instead of emitting them as sibling =KeywordLine= nodes.

This is the v0 metadata hook for named tables, inline chart declarations, and SQL/dataset views. The keyword payload remains opaque in the canonical AST; higher-level APIs may interpret values such as =#+chart: line x=quarter y=revenue= or =#+view: finance.revenue_by_quarter=.

If an affiliated key is followed by a blank line, headline, paragraph, drawer, planning line, comment, or any other non-eligible element, it MUST remain a standalone =KeywordLine= node.

* Planning lines (SCHEDULED:/DEADLINE:/CLOSED:)

Org2 v0 recognizes planning lines as explicit nodes:

- =SCHEDULED: ...=
- =DEADLINE: ...=
- =CLOSED: ...=

Planning lines produce a =Planning= node with:

- =kind=: =SCHEDULED=, =DEADLINE=, or =CLOSED=
- =raw=: the exact original line
- =timestamp= (optional): the first timestamp or timestamp range found in the remainder

Planning semantics are out of scope for v0.

* Common blocks (example/quote/verse/center)

Org2 v0 supports parsing common block types as a lossless structural node.

Recognized begin/end pairs are matched ASCII case-insensitively:

- =#+begin_example= / =#+end_example=
- =#+begin_quote= / =#+end_quote=
- =#+begin_verse= / =#+end_verse=
- =#+begin_center= / =#+end_center=

Each produces a =Block= node with:

- =kind=: one of =example|quote|verse|center=
- =terminated=: whether a matching end marker was found
- =begin= / =end=: captured as =indent=, =keywordRaw=, =afterKeywordRaw=
- =bodyRaw=: raw bytes between begin and end lines
