#+TITLE: Language reference

This is the practical language reference for Celorga's Org profile, v0.

For the normative draft standard, start with [[https://github.com/aviaviavi/celorga/blob/main/spec/v0/SPEC.org][SPEC.org]]. The standard is independently implementable: its surface grammar, contextual parsing algorithms, canonical AST schema, and executable conformance cases are all public.

* Spec map

Use this mapping when deciding where behavior is defined:

- Language overview and construct requirements: [[https://github.com/aviaviavi/celorga/blob/main/spec/v0/SPEC.org][SPEC.org]]
- Normative surface grammar: [[https://github.com/aviaviavi/celorga/blob/main/spec/v0/GRAMMAR.ebnf][GRAMMAR.ebnf]]
- Parsing precedence, grouping, and AST construction: [[https://github.com/aviaviavi/celorga/blob/main/spec/v0/PARSING.org][PARSING.org]]
- Canonical AST and executable conformance: [[https://github.com/aviaviavi/celorga/blob/main/spec/v0/canonical-ast.schema.json][canonical-ast.schema.json]] and [[https://github.com/aviaviavi/celorga/blob/main/spec/v0/parsing-cases.json][parsing-cases.json]]
- Roam semantics (IDs, links, backlinks model): [[https://github.com/aviaviavi/celorga/blob/main/spec/v0/ROAM.org][spec/v0/ROAM.org]]
- CLI/editor workflow behavior: [[file:tooling-reference.org][Tooling reference]]

* Headings

- Syntax: one or more stars, a space, then title text.
- Example:

#+begin_src org
* Project
** Subproject
*** Task
#+end_src

- Heading level is the number of stars.
- Level skips are accepted in v0.

* TODO keywords

Headline TODO states parsed into the canonical AST:

- =TODO=
- =IN_PROGRESS=
- =DONE=
- =CANCELLED= / =CANCELED=

Workflow tools may accept aliases such as =PROG= or =WAITING= and normalize them to one of the canonical TODO keywords above.

Corpus defaults live in =celorga.json= under =todo.sequences=, for example ={"todo":{"sequences":["TODO WAITING | DONE SKIPPED"]}}=. Celorga exposes these under Settings → General → TODO States. Each corpus sequence needs an active state and a terminal state; state names must be unique across the corpus sequences. An empty array restores built-in defaults.

Files may also declare their own Org-compatible vocabulary with =#+TODO:=, =#+SEQ_TODO:=, or =#+TYP_TODO:=. Fast-selection suffixes such as =WAITING(w)= are recognized and omitted from the stored headline state:

#+begin_src org
#+TODO: IDEA(i) WAITING(w) | SHIPPED(s)
* WAITING Publish the package
#+end_src

File-local declarations replace the corpus sequences for that file. Without a file-local declaration, parsing, editing, agendas, and compiled context use the nearest corpus configuration.

States before =|= are active; states after it are terminal (no further action required). Without =|=, the last keyword is terminal. Multiple declarations define independent sequences. Keywords retain their spelling and case. Built-in states remain available. Declarations inside source/example blocks and drawers do not change the workflow.

Custom states work in TODO mutations, agenda filtering, and Celorga heading controls. Terminal states do not become overdue tasks; reopening clears =CLOSED=. Shortcut and logging annotations are accepted, but their Emacs-specific interactive prompts/keybindings are not implemented.

Example:

#+begin_src org
* TODO Ship docs
* IN_PROGRESS Implement parser tests
* DONE Publish changelog
#+end_src

* Priority cookies

- Syntax: =[#A]= style cookie after TODO keyword (or at headline start when no TODO keyword).

#+begin_src org
* TODO [#A] Critical task
#+end_src

A file may set its range with =#+PRIORITIES: HIGHEST LOWEST DEFAULT=, either as letters (=#+PRIORITIES: A E C=) or digits (=#+PRIORITIES: 1 5 3=); without it the range is =A= to =C= with default =B=. A cookie is one letter or digit, so =[#AA]= and =[#-1]= are not cookies. =celorga lint= and the LSP warn about cookies outside the range, invalid or unclosed cookies, and an invalid =#+PRIORITIES:= line.

Priority is stored as the dedicated =priority= headline field. Org's =COMMENT= headline marker is stored as =commented: true= while all source bytes still round-trip unchanged.

* Tags

- Tags are suffixes at headline end: =:tag:= or =:tag1:tag2:=

#+begin_src org
* TODO Draft docs :docs:website:
#+end_src

* Drawers

** Property drawers

- Drawer delimiters: =:PROPERTIES:= ... =:END:=
- Consistently space-indented property drawers are accepted for legacy files. =celorga fmt= canonicalizes their delimiter and property lines to column zero.
- Common keys used by Celorga workflows:
  - =:ID:=
  - =:CUSTOM_ID:=
  - =:EFFORT:=
  - =:ROAM_ALIASES:=

#+begin_src org
:PROPERTIES:
:ID: 123e4567-e89b-12d3-a456-426614174000
:EFFORT: 45
:END:
#+end_src

** Generic drawers

- Generic =:NAME:= ... =:END:= drawers are preserved.

* Planning lines

Recognized planning keywords:

- =SCHEDULED:=
- =DEADLINE:=
- =CLOSED:=

#+begin_src org
SCHEDULED: <2026-02-21 Sat>
DEADLINE: <2026-02-25 Wed>
CLOSED: [2026-02-20 Fri]
#+end_src

* Timestamps

Supported timestamp forms:

- Active: =<2026-02-21 Sat>=
- Inactive: =[2026-02-21 Sat]=
- With time: =<2026-02-21 Sat 09:30>=
- Ranges: =<2026-02-21 Sat>--<2026-02-23 Mon>=
- Repeaters (agenda projection): =+1w=, =++1m=, =.+2d=

* Lists

- Unordered markers: =-=, =+=, =*=
- Ordered markers: =1.=, =1)=
- Checkboxes: =[ ]=, =[X]=, =[x]=, =[-]=
- Cycle a list checkbox with =celorga checkbox --file FILE --line N --apply=: =[ ]= → =[-]= → =[X]= → =[ ]=. The CLI and LSP code action change only the selected marker; see [[file:tooling-reference.org][Tooling reference]].
- Checkbox progress cookies: =[n/m]= and =[p%]= may appear in headings or list items; =[/]= and =[%]= are empty placeholders. Compile output and lint compare each cookie with its innermost containing heading total. Checked items count as completed; unchecked and indeterminate items count only toward the total. =celorga checkbox fix-cookies --file FILE --apply= writes corrected values, while =celorga checkbox cycle --file FILE --line N --fix-cookies --apply= changes a marker and refreshes cookies atomically.
- Nested lists via indentation.
- Counter cookies such as =[@3]= are stored separately from the written ordered-list marker.
- Descriptive items use =term :: definition= and render as description lists.

* Links

Supported link forms:

- Bracket links: =[[https://example.com][label]]=
- Plain URLs: =https://example.com=
- File links: =[[file:path/to/file.org]]=
- ID links: =[[id:UUID][label]]= (roam-style link)
- Wiki links: =[[Node Title]]= (roam-style link)
- Angle links: =<mailto:hello@example.com>=
- Targets: =<<name>>= and radio targets =<<<name>>>=

Both ID links and Wiki links are first-class in Celorga roam workflows.

Link abbreviations are supported with built-ins, config, and =#+LINK= directives.

Built-in abbreviations:
- =gh:= → =https://github.com/%s=
- =gl:= → =https://gitlab.com/%s=
- =yt:= → =https://www.youtube.com/watch?v=%s=
- =wiki:= → =https://en.wikipedia.org/wiki/%s=

You can add/override abbreviations in =celorga.json=:

#+begin_src json
{
  "links": {
    "linearTeam": "acme",
    "abbreviations": {
      "linear": "https://linear.app/acme/issue/%s",
      "gh": "https://github.example.com/%s"
    }
  }
}
#+end_src

And define file-local abbreviations with Org-compatible syntax:
- Define: =#+LINK: linear https://linear.app/acme/issue/%s=
- Use: =[[linear:APP-3718][APP-3718]]= or =[[linear:APP-3718]]=

Precedence (highest to lowest):
1) file-local =#+LINK=
2) =celorga.json= links.abbreviations
3) built-ins

Celorga expands abbreviation targets when rendering/exporting and for LSP document-link targets.

* Corpus identity

The root =celorga.json= may identify the corpus independently of its local path:

#+begin_src json
{
  "corpus": {
    "schema": "celorga:corpus:v1",
    "id": "team-operations",
    "name": "Team Operations",
    "kind": "shared"
  }
}
#+end_src

=id= is a stable lowercase slug, =name= is the human-facing label, and =kind= is =personal=, =shared=, or =project=. This record is portable. Local mount paths, credentials, and membership stay outside the corpus. See [[file:collaboration.org][Shared corpora and collaboration]] and =spec/v0/corpus.schema.json=.

* Inline emphasis

- Bold: =*bold*=
- Italic: =/italic/=
- Underline: =_underline_=
- Strike: =+strike+=
- Verbatim: ==verbatim==
- Code: =~code~=, with Markdown-style =`code`= accepted as shorthand

* Rich inline objects

Celorga also parses the everyday publishing and scholarly inline objects used by Org:

- Footnote references: =[fn:label]=, =[fn:label:inline definition]=, and =[fn::anonymous definition]=
- Citations: =[cite:@key]= and multi-reference/style forms such as =[cite/t:@doe; see @roe p. 4]=
- Entities: =\alpha=, =\copy=, =\rarr=, and other common Org entities
- LaTeX fragments: =$x_2$=, =$$x = y$$=, =\(...\)=, and =\[...\]=
- Export snippets: =@@html:<mark>highlighted</mark>@@=
- Subscripts and superscripts: =H_2O= and =x^{2}=
- Explicit line breaks: two backslashes at the end of a line

These are first-class canonical AST objects and render in the CLI, published HTML, and Mac/iOS document views. Export snippets are emitted as raw HTML only by the publishing renderer; app previews escape their payload.

Footnote definitions use the ordinary Org form:

#+begin_src org
The claim has a source.[fn:source]

[fn:source] Supporting detail.
#+end_src

* Blocks

Recognized block forms include:

- Source blocks: =#+begin_src ... #+end_src=
- Example blocks: =#+begin_example ... #+end_example=
- Quote blocks: =#+begin_quote ... #+end_quote=
- Verse blocks: =#+begin_verse ... #+end_verse=
- Center blocks: =#+begin_center ... #+end_center=
- Comment blocks: =#+begin_comment ... #+end_comment=
- Arbitrary special blocks: =#+begin_NAME ... #+end_NAME=
- Dynamic blocks: =#+begin: NAME ... #+end:= (parsed and preserved; Celorga does not execute dynamic-block writers)
- LaTeX environments: =\begin{equation} ... \end{equation}=
- Fixed-width lines beginning with a colon followed by one space
- Horizontal rules of five or more hyphens
- Diary sexps beginning with =%%(=

** Syntactic sugar / aliases

Celorga accepts a friendlier fenced-code typing alias for source blocks:

#+begin_example
```ts
const x = 1
```
#+end_example

This is treated as syntactic sugar for:

#+begin_example
#+begin_src ts
const x = 1
#+end_src
#+end_example

New =.org= documents use the ordinary Org form on disk. Celorga, file-based CLI formatting, the LSP, and editor integrations rewrite fences to =#+begin_src= / =#+end_src= and backtick inline code to ordinary Org inline markup whenever edited =.org= source is persisted or formatted. This syntax canonicalization still occurs when general format-on-save is disabled: the input remains quick to type, while persisted =.org= files stay valid Org syntax.

File-based CLI formatting selects the profile automatically from the extension. Stdin has no filename, so buffer-oriented callers select it explicitly:

#+begin_src sh
celorga fmt --stdin --canonical-org
celorga fmt --file note.org --apply
#+end_src

Fenced source blocks use exactly three backticks for the opener and closer. Four-or-more backticks remain ordinary text in v0, which keeps Markdown examples that quote celorga fences from accidentally becoming executable celorga source, chart, dataset, or SQL blocks.

* Tables

- Pipe table rows: =| a | b |=

Celorga defines the custom link type =color:= as explicit, non-navigating presentation markup. Use =[[color:red][urgent]]= for foreground color, =[[color:bg=yellow][review]]= for background color, or =[[color:fg=white;bg=#b42318][blocked]]= for both. Keys may be abbreviated as =fg=/=bg= or written as =foreground=/=background=; =text= is also accepted for foreground. Values may be supported names or three/six-digit hex literals.

The portable named palette is =black=, =blue=, =brown=, =gray=/=grey=, =green=, =indigo=, =mint=, =orange=, =pink=, =purple=, =red=, =teal=, =white=, and =yellow=. Hex literals provide exact custom colors without allowing arbitrary CSS.

The binding works anywhere links are parsed, including prose, headings, and table cells. In ordinary inline content, background color applies to the labeled span. When one color binding occupies an entire table cell, rendered clients apply its foreground and background to the whole cell. It remains a normal bracket link in the canonical AST and round-trips byte-for-byte, so standard Org tools preserve the label even when they do not interpret the =color:= type. Invalid color declarations remain ordinary links rather than accepting arbitrary CSS.
- Horizontal separator rows: =|---+---|=
- Table content is parsed and preserved. Each row retains compatible raw =cells= strings and also exposes parallel structured =contents= inline objects.

Org table formulas are attached to their preceding table as structured =TableFormulaLine= nodes and can be recalculated safely:

#+begin_src org
| item | qty | price | total |
|------+-----+-------+-------|
| A    |   2 |  3.50 |       |
| B    |   4 |  2.00 |       |
#+TBLFM: $4=$2*$3;%.2f
#+end_src

=celorga table recalculate --file report.org= previews the changed cells; add =--apply= to write them atomically. The Mac rendered view evaluates supported formulas for display and offers the same explicit recalculation action for editable files. HTML export uses the shared evaluator without rewriting source.

The safe formula subset includes field, row, column, and rectangular-range assignments; absolute and relative =@row$column= references; A1 references; arithmetic, comparisons, and boolean operators; =vsum=, =vmean=, =vmin=, =vmax=, =vmedian=, =vcount=, common numeric functions; printf/Calc-style numeric formats; and =T=, =U=, and =t= duration modes. Later assignments override earlier assignments for the same cell. Empty-field =N= mode is supported. Formula lines, including unsupported forms, remain lossless.

Celorga deliberately does not execute Emacs Lisp formulas, remote-table references, or arbitrary Calc extensions. An unsupported or invalid formula produces a diagnostic and leaves the source unchanged rather than partially updating a table.

* Deliberate compatibility boundary

Celorga now covers most Org syntax used for notes, planning, publishing, linking, and scholarly prose. It deliberately does not implement macro expansion, Babel execution, inline source/call evaluation, or dynamic-block execution. Inline tasks remain ordinary deep headlines rather than a separate execution construct. Unsupported execution-oriented forms remain losslessly preserved as text or directives.

Tables, source blocks, and common blocks can carry adjacent affiliated keyword metadata:

#+begin_src org
#+name: quarterly_revenue
#+chart: line x=quarter y=revenue
#+dataset: finance.revenue
| quarter | revenue |
|---------+---------|
| 2026-Q1 | 1200    |
#+end_src

Recognized affiliated keys include =NAME=, =CAPTION=, =PLOT=, =CHART=, =DATASET=, =VIEW=, =RESULTS=, =HEADER=/=HEADERS=, and =ATTR_*= keys. The parser preserves them on the following table or block as =affiliatedKeywords= for chart renderers, dataset indexes, SQL views, and exporters.

Canonical =.org= documents use an adjacent chart source block:

#+begin_example
#+name: fetch_buckets
| bucket | fetches |
|--------+---------|
| 0-10   | 14      |
| 11-50  | 32      |

#+begin_src chart histogram
x: bucket
y: fetches
sort: y-desc
source: previous-table
#+end_src
#+end_example

This is chart metadata over the preceding table. Chart source blocks may also point at a named table or materialized result elsewhere in the same note; fenced chart input remains accepted as typing sugar:

#+begin_example
#+name: package_fetches_result
#+results: query-fetches-by-company
| day        | fetches |
|------------+---------|
| 2026-06-10 | 84      |

#+name: package_fetches_chart
#+begin_src chart line
x: day
y: fetches
source: package_fetches_result
size: compact
height: 300
interactive: true
#+end_src
#+end_example

The current renderer supports =bar=, =line=, and bucketed =histogram= charts over the previous table or a named table source. Add =sort: x-asc=, =sort: x-desc=, =sort: y-asc=, or =sort: y-desc= when the visual should order marks independently of the table's source row order. =size= accepts =compact=, =medium=, or =wide=. =height= accepts 220–720 pixels and defaults according to the size preset. =interactive= defaults to =true=; in the Mac app's documents and AI chat it enables nearest-point hover, exact-value tooltips, a crosshair, keyboard navigation between marks, and legend toggling that hides or shows a series (the last visible series stays). Static SVG remains the canonical CLI and export fallback.

A chart block may also carry its own data: table rows written inside the block are used instead of the previous table, which keeps a chart self-contained in a chat reply or a short note. An explicit =source:= still wins.

#+begin_example
#+begin_src chart bar
x: package
y: downloads
| package | downloads |
|---------+-----------|
| alpha   | 1200      |
| beta    | 800       |
#+end_src
#+end_example

Line and bar charts may render multiple numeric columns against the same x-axis. List the columns in =y= (or =series= inside a chart source block), separated by commas:

#+begin_example
#+name: quarterly_metrics
| quarter | revenue | cost | profit |
|---------+---------+------+--------|
| 2026-Q1 | 1200    | 700  | 500    |
| 2026-Q2 | 1500    | 825  | 675    |

#+begin_src chart line
x: quarter
y: revenue, cost, profit
source: quarterly_metrics
#+end_src
#+end_example

Each line receives a stable color from the chart series style variables listed below, which Celorga sets from the selected light or dark theme, and grouped bar charts place each series beside the others within its x-axis category. Multi-series charts include a legend, series-aware accessibility labels, and series names in interactive tooltips. A =y-asc= or =y-desc= sort uses the first listed series. Histograms remain single-series because each row already represents one bucket.

Charts are drawn in a clean, modern style. Lines are smooth (monotone, so they never overshoot the data); a one- or two-series line chart gets a soft gradient fill; and each line ends in a dot labeled with its latest value, with the series name when there are several. Line charts fit the value axis to the data rather than always starting at zero, while bar charts always include zero and label each bar when there is room. Axis labels stay horizontal: long category names are shortened (the full name stays available as a tooltip) or thinned out. Values use compact units such as =95.9k= or =24M=; a currency prefix appears when every cell starts with =$= or the column name contains =usd=, and a percent suffix appears when every cell ends in =%= or the name contains =pct= or =percent=. Cells such as =$1,200= and =12%= are read as numbers. Tooltips show the full value, for example =$95,880=.

The Mac app treats chart interaction as app-owned presentation behavior. Notes cannot provide arbitrary JavaScript. Chart cards can also be resized horizontally in the rendered view; use =size= and =height= when the desired dimensions should remain deterministic in source.

Chart SVG uses CSS custom properties with opinionated defaults: =--celorga-chart-mark=, =--celorga-chart-series-2= through =--celorga-chart-series-8=, =--celorga-chart-surface=, =--celorga-chart-axis=, =--celorga-chart-grid=, =--celorga-chart-label=, and =--celorga-chart-title=. Set them on =.celorga-chart= in a published stylesheet or the Mac app's =.celorga/app.css= to customize the visual theme without changing the data declaration.

The CLI can render chart-affiliated tables directly:

#+begin_src sh
celorga render-chart --file report.org --block-id quarterly_revenue --format svg
#+end_src

* Local datasets and SQL views

Celorga can describe local/ad hoc data workflows with =dataset= and =sql= source blocks. Equivalent fences remain accepted as typing sugar. This is intended for notebook-like reports over explicit local files, read-only URLs, and named Org tables, with DuckDB as the first execution bridge:

#+begin_example
#+begin_src dataset fetches
type: csv
path: ./data/package-fetches.csv
engine: duckdb
#+end_src

#+begin_src sql results=fetches_by_state artifact=views/fetches_by_state.org freshness=24h
SELECT state, count(*) AS fetches
FROM fetches
GROUP BY state
ORDER BY fetches DESC
#+end_src

#+begin_src chart bar
source: fetches_by_state
x: state
y: fetches
#+end_src
#+end_example

=celorga query-data= reads these blocks, creates DuckDB views for local files, URL-backed sources, named celorga tables, or configured remote analytics datasets, creates declared SQL views, runs a selected SQL result block through the local DuckDB CLI, and materializes the returned rows as a named org table or JSON envelope. Materialized org tables include a =#+query-data:= provenance line with the result id, row count, optional freshness token, selected SQL hash, full DuckDB script hash, and =ran_at= timestamp:

#+begin_src sh
celorga query-data --file report.org --results fetches_by_state --out report.fetches.org
celorga query-data --file report.org --results fetches_by_state --apply
celorga query-data --file report.org --line 42 --format json
celorga query-data --file report.org --inspect --include-script
cat report.org | celorga query-data --stdin --results fetches_by_state --format json
#+end_src

Use =--stdin= when an editor, agent, or notebook-style client wants to run the current buffer without saving it first. Use =--line N= to select the SQL result block containing or after the cursor line. JSON output includes =resultBlocks= with each available SQL result id and source range. Use =--inspect= to return parsed datasets, SQL views, result metadata, diagnostics, and selected-query provenance without running DuckDB; =--include-script= also returns generated DuckDB SQL. Relative file paths are resolved from the working directory for stdin input. SQL result ids must be unique, and dataset ids and SQL view ids must be distinct because they become DuckDB relation names. Local URL/table datasets may carry metadata-only credential/config references such as =env:SCARF_API_TOKEN= or =profile:product-analytics=; remote analytics datasets use their named profile operationally but never insert credentials into generated SQL. Inline bearer tokens, passwords, and other literal secrets are rejected. SQL result blocks can include =artifact=PATH= and =freshness=24h= / =ttl=24h= / =max-age=24h= metadata. Executed results stamp =ranAt= so clients can evaluate freshness.

Use =sql view=NAME= when a report needs a reusable local projection before the final result table:

#+begin_example
#+begin_src sql view=california_fetches
SELECT state, fetches
FROM fetches
WHERE state = 'CA'
#+end_src

#+begin_src sql results=fetches_by_state
SELECT state, sum(fetches) AS fetches
FROM california_fetches
GROUP BY state
#+end_src
#+end_example

Use =url:= instead of =path:= when DuckDB should read a declared HTTP(S) or =file:= URL directly:

#+begin_example
#+begin_src dataset remote_fetches
type: csv
url: https://data.example.test/package-fetches.csv
engine: duckdb
credential: env:SCARF_API_TOKEN
config: profile:product-analytics
#+end_src

#+begin_src sql results=remote_fetches_by_state
SELECT state, count(*) AS fetches
FROM remote_fetches
GROUP BY state
#+end_src
#+end_example

** Remote analytics datasets

Remote datasets use the same named-dataset and DuckDB result pipeline as local CSV files. A note names a profile, but never contains a warehouse URL, API key, username, or password. Profiles live in the nearest =celorga.json= and refer to secrets through environment-variable names:

#+begin_src json
{
  "dataSources": {
    "scarf-clickhouse": {
      "type": "clickhouse",
      "url": "https://clickhouse.example.com/",
      "database": "analytics",
      "userEnv": "SCARF_CLICKHOUSE_USER",
      "passwordEnv": "SCARF_CLICKHOUSE_PASSWORD",
      "timeoutMs": 300000,
      "maxRows": 10000
    },
    "scarf-metabase": {
      "type": "metabase",
      "url": "https://metabase.example.com/",
      "apiKeyEnv": "SCARF_METABASE_API_KEY",
      "databaseIdEnv": "SCARF_METABASE_DATABASE_ID",
      "timeoutMs": 300000,
      "maxRows": 10000
    }
  }
}
#+end_src

A ClickHouse dataset carries read-only SQL:

#+begin_example
#+begin_src dataset package_fetches
type: clickhouse
profile: scarf-clickhouse
query: |
  SELECT toDate(timestamp) AS day, count() AS fetches
  FROM package_downloads
  WHERE timestamp >= now() - INTERVAL 30 DAY
  GROUP BY day
  ORDER BY day
#+end_src
#+end_example

A Metabase dataset executes a saved question by numeric question/card ID. Optional =parameters: |= is JSON using Metabase's parameter payload format:

#+begin_example
#+begin_src dataset revenue
type: metabase
profile: scarf-metabase
question: 123
parameters: |
  []
#+end_src
#+end_example

For a reproducible notebook, put the native SQL directly in the dataset block instead of relying on a mutable saved question. The profile must provide either a positive =databaseId= or a =databaseIdEnv= naming an environment variable that contains it:

#+begin_example
#+begin_src dataset recent_organizations
type: metabase
profile: scarf-metabase
query: |
  SELECT name, billing_email, created_at
  FROM organizations
  ORDER BY created_at DESC
  LIMIT 25
#+end_src
#+end_example

Use either dataset in ordinary DuckDB SQL, materialize the result as an Org table with =celorga query-data=, then attach a =#+begin_src chart= block to that named result. ClickHouse requests set server-side read-only mode, row limits, execution timeouts, and JSON output. Metabase requests use API-key authentication and saved-question JSON export. Both adapters enforce response-size and row limits locally as well.

For notebooks with multiple remote sources, declare each result's dependency edge explicitly with =sources=DATASET_ID[,DATASET_ID...]=. Celorga validates the named sources, loads only those datasets for that result, and records them in materialization provenance:

#+begin_example
#+begin_src sql results=recent_organizations sources=recent_organizations_source freshness=24h
SELECT * FROM recent_organizations_source
ORDER BY created_at DESC
#+end_src
#+end_example

Refreshing data is always explicit. Use =celorga query-data --apply= to insert the selected result after its SQL block or replace the existing provenance-stamped result in place. HTML rendering and opening a note in the Mac app only consume tables already present in the document; they never contact Metabase or ClickHouse. Valid chart declarations over those tables are rendered automatically as responsive inline SVG in the Mac app and static HTML exports.

Use =type: table= with =source: NAME= when the source data already lives in a named Org table:

#+begin_example
#+name: raw_fetches
| state | fetches |
|-------+---------|
| CA    | 42      |
| NY    | 24      |

#+begin_src dataset fetches
type: table
source: raw_fetches
engine: duckdb
#+end_src

#+begin_src sql results=fetches_total
SELECT sum(fetches) AS fetches
FROM fetches
#+end_src
#+end_example

This is deliberately scoped to explicit local/ad hoc data sources. Celorga stores the source path, read-only URL, table/view name, optional column and primary-key metadata, credential/config reference, query, and materialized result/provenance; secrets, bearer tokens, and remote warehouse credentials belong in external tooling, not in notes.

* Presentations

Celorga can compile an Org-shaped outline into a backend-neutral presentation model and render that model as Beamer LaTeX or PDF:

#+begin_src sh
celorga export beamer --file talk.org
celorga export beamer --file talk.org --out talk.tex --apply
celorga export beamer --file talk.org --out talk.pdf --pdf --apply
#+end_src

Export previews by default. =--pdf= invokes =pdflatex= twice; use =--latex-engine COMMAND= to select another installed LaTeX engine.

For pdfLaTeX compatibility, common Unicode arrows, comparison operators, checkmarks, bullets, dashes, and related symbols are translated to equivalent LaTeX commands in prose, headings, metadata, and literal/source blocks. This includes symbols such as =→=, =↘=, =≥=, and =✓= that pdfLaTeX's default UTF-8 layer does not define directly.

The frame level defaults to 2 and follows the familiar Org convention in =#+OPTIONS: H:2=: level-one headlines become sections and level-two headlines become slides. =#+CELORGA_SLIDE_LEVEL:=, =#+SLIDE_LEVEL:=, and legacy =#+BEAMER_FRAME_LEVEL:= can set the level explicitly. =toc:t= adds an outline frame.

A minimal talk is ordinary Org-shaped text:

#+begin_src org
#+TITLE: Shipping a local-first compiler
#+AUTHOR: Example Speaker
#+OPTIONS: H:2 toc:t
#+BEAMER_THEME: Madrid

* Why
** Plain text is the interface
- Reviewable in Git
- Editable anywhere
- One source → slides, sites, and agent context

* How
** Shared semantics
The compiler parses once and renders each target from the same structure.
#+end_src

Document metadata and Beamer compatibility keywords include:

- =#+TITLE:=, =#+AUTHOR:=, =#+DATE:=
- =#+LATEX_CLASS_OPTIONS:=
- =#+BEAMER_THEME:=, =#+BEAMER_COLOR_THEME:=, =#+BEAMER_FONT_THEME:=
- =#+BEAMER_INNER_THEME:=, =#+BEAMER_OUTER_THEME:=
- repeatable =#+LATEX_HEADER:= and =#+BEAMER_HEADER:=

Headlines below a slide become presentation groups. Legacy properties remain accepted so existing Org Beamer talks can move over incrementally:

| Celorga property | Legacy alias | Meaning |
|---------------+--------------+---------|
| =SLIDE_ENV= | =BEAMER_ENV= | =block=, =note=, =ignoreheading=, or =plain= |
| =SLIDE_COLUMN= | =BEAMER_COL= | column width such as =0.45= or =45%= |
| =SLIDE_REVEAL= | =BEAMER_ACT= | overlay such as =<2->= or =3-= |
| =SLIDE_ROLE: note= | =BEAMER_ENV: note= | speaker note content |

The =:B_note:= tag is also accepted for legacy notes. Source blocks make their frame =fragile=. Lists, nested blocks, quotes, tables, links, inline emphasis, images, and =#+ATTR_LATEX= image sizing render through the shared syntax tree. A =#+RESULTS:= image immediately following a source block is omitted from Beamer output, matching Org's default code-export behavior.

Backend-specific escape hatches remain explicit and reviewable:

#+begin_src org
#+LATEX: \pause

#+BEGIN_EXPORT beamer
\vfill
#+END_EXPORT
#+end_src

Relative image paths resolve from the source file's directory during PDF compilation. Unknown slide environments produce warnings rather than being silently discarded.

The macOS Workspace exposes the same pipeline as an embedded *View → Slides* PDF preview, including live compilation from an unsaved source-editor draft, and through *File → Export Slides as PDF…* and *File → Export Slides as LaTeX…*. See [[file:editors-macos.org][macOS Workspace → Slide preview and export]] for the application workflow and troubleshooting.

* Keyword/directive lines

Celorga parses keyword lines in =#+KEY: VALUE= form.

Commonly used in export/publish:

- =#+TITLE:=
- =#+SUBTITLE:=
- =#+AUTHOR:=
- =#+DATE:=
- =#+DESCRIPTION:=
- =#+KEYWORDS:=
- =#+LANGUAGE:=
- =#+HTML_HEAD:=
- =#+LATEX_CLASS_OPTIONS:=
- =#+LATEX_HEADER:=
- =#+BEAMER_THEME:=
- =#+ID:=

Unknown directives are preserved for round-tripping.

* Comments

- Line comments: lines beginning with =#=.
- Comment blocks are also supported (see Blocks).

* Losslessness goal

Celorga aims for practical round-tripping of supported constructs.
When behavior is ambiguous, defer to the current implementation and spec fixtures.
